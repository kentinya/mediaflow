## 2026-10-11：文件夹整理修正 Task 的范围收敛

MediaFlow Slice 44 的[完整旅程审查](../reviews/slice-44-folder-organize-audit.md)发现八组问题。
最初 Task 44.9 虽归并为一个任务，仍要求精确断点续跑、跨配置切换的原申请自动恢复、
复杂控制竞态下保留所有未落盘工作，以及广泛的旧任务恢复，因此实现负担仍然偏重。

用户明确要求简化后，A 提交恢复范围调整，再以已授权的规划例外重新评估 Task。
Task 44.9 当时仍为 PLANNED、没有实现 checkpoint，因而保留原 ID/Base，合法调整 Goal、Scope
和恢复验收，保留普通功能修正、安全约束与 High / T4。B 仍承担独立实现审查。

案例依据是 Contract 提交 `7e96ebf314e4eab22a72d98028a775f248118138` 和规划提交
`7f9bec8896ce5a30ecba5ea9a55924b8f2df7af3`。这是范围与规划已经收敛的经验，
不是 Developer 已完成、B 已 PASS 或实际工时已经减少的记录。后续状态查实际仓库与验证。

## 1. 从已提交的 Contract 规划完整行为

先核实 Slice 的真实状态、Base、当前 Task 和代码；运行现行治理检查，再规划。
Task 围绕一个可审查的完整行为覆盖必要的 Domain、Persistence、Application、API、Web 和测试，
不按文件、字段或一个断言机械拆分。

八组缺陷不等于八个 Task。本次都围绕同一个发现与整理交接旅程，可以形成一个连贯修正任务，
但合并成一个文档也不会自动降低工程复杂度。B 仍应检查是否有独立业务目标、隐藏依赖或过多新增机制。
3–7 个 Task 是大型 Slice 的规划参考，不是必须凑够的数量；预计超过 8 个或持续补丁循环时，
按现行工作流重新评估 Task 粒度和 Slice 边界，而不是自动追加编号。

## 2. 反复修正时检查跨层语义，而不只补失败点

本次问题集中在多层对同一业务事实理解不一致：

| 业务事实 | 规划需要核实的连贯关系 |
|---|---|
| 用户配置已经生效 | 页面保存、验证、发布、生产加载器与 Worker 消费同一个不可变配置 |
| 文件夹已经完整发现 | 文件和目录错误都影响完整性；预算拒绝与普通读取失败不能互相掩盖 |
| 来源是独立主媒体 | 发现、附件关联、主媒体计数和预览使用一致语义，不能把匹配 Trailer 当第二部电影 |
| 等待文件稳定 | 真实观察间隔、领取时机、预算和其他常驻工作可以一致推进 |
| 同一申请只入队一次 | 规范化范围和持久化原子判断一致，不依赖最近列表窗口 |

如果只在报错处增加 fallback、吞异常或放宽上限，往往会把错误移到下一层。
B 应规划最小的跨层修正，并优先复用已有规则与权威来源；这不授权大规模无关重构。

## 3. 将范围问题交还 A，不自行降低验收

业务目标文字没变，也可能发生实质范围变化。将“保证自动继续”改成“安全停止后重新发现”，
会改变恢复义务和当前 Task 的验收，不能由 B 修改测试、降低 Difficulty 或改 wording 代替。

先由 A 修改并提交 Contract，再由 B 明确重新判断 Task 是继续、合法调整还是重新规划。
本次同 ID/Base 调整成立的具体条件是：Task 仍为 PLANNED、没有实施 checkpoint，且新的 A Contract
已经提交。它不是处理所有已实施任务的通用模板，也不是允许 B 任意改 Goal/Scope 的规则。

规划结果应明确旧义务中哪些仍须完成、哪些已被合法替代，并保留历史证据。
被延后的自动恢复不能记作已修复；错误根目录或配置绑定仍然必须修正。
用户授权 A 代规划也不代表 Developer 可自行规划或 B 的独立审查被取消。

## 4. 以最小机制满足当前承诺

本次保留有界后台发现、真实过滤与稳定性、正常暂停继续取消、逐项错误及精确预览执行；
无法安全续跑的未冻结发现可以明确停止，再由用户新建发现。
因此不再要求新增通用游标续跑框架、任意竞态无损恢复或所有历史异常自动修复。

这种替代路径仍需要持久记录、错误解释、原生操作入口和旧尝试的安全停止；
不能退化为吞异常、无限排队或只显示“重试”。未知提交只能恢复已经证明的原申请，
否则显示未确认状态并供用户查看与解决，不能猜测或自动重提。

低概率不自动等于可忽略。廉价的正确计数、合法输入处理和真实状态投影仍应修正；
涉及安全的极端条件仍须覆盖。需要大量新状态与兼容逻辑的增强连续性，才适合请求 A 判断范围取舍。
对其他项目也先区分可重新计算的分析与可能发生真实写入的阶段，后者不能套用重新运行策略。

## 5. 难度、测试风险与执行成本分别规划

范围缩减不必然降低 Difficulty 或 Test Level。配置发布、并发、持久状态演进与核心执行交接
仍能使任务保持 High / T4；这不意味着必须重建全部架构。
指出最难接通的边界和可直接复用的部分，比泛称“只是几个 bug”更有助于 Developer。

开发反馈先跑失败案例和受影响测试，修正已知问题后，再完成当前候选的最终等级要求。
完整套件若已经覆盖同配置的聚焦用例，可记录覆盖关系；B 不因审查人不同而机械重跑每个完整检查。
这不允许省略已分配的 T4 门槛，实际源代码或输入改变后仍要按工作流刷新相关证据。

选择能证明业务错误的最小测试。分页计数可以用降低目录预算的多页本地样本验证正确单位，
无需重复所有历史 HTTP 页数。稳定性要证明真实间隔，不能只用修改时间代替。
托管配置必须验证实际发布与生产读取，领域注入仅是补充；原生 Web 旅程也不能被 mock 返回值替代。

## 6. 按当前验收独立审查，并执行停止规则

审查实际 Task Base..提交 Head、生产行为和可核实证据，不将测试总数或完成报告当作产品结论。
重点独立复现普通旅程和关键风险；复用其他证据时核对源代码、配置、构建资产及运行条件。
PASS、FAIL、SKIP、UNAVAILABLE 保持事实含义，历史通过结果不自动覆盖新实现。

如果 A 已明确缩减恢复承诺，旧测试中的无缝续跑期待可以按新 Contract 调整，但需要记录原测试、
变化和依据，并保留真实失败、不可非法冻结、配置与所有权隔离、不重放的断言。
这与删掉仍要求的安全测试来获得 PASS 有本质区别。

达到当前 Task 验收后重新评估全部 Slice Required Outcomes。全部满足就准备 Closure Packet 交 A；
未满足则依据实际缺口安排连贯工作。P2/P3、额外证明、wording、可选 cleanup 和未来能力
不单独产生新 Task，也不能因“还可以测更多”持续延长修正链。B 不宣告 Slice PASS/CLOSED。

## 后续积累方式

追加经验时记录触发情况、实际证据、规划或审查决策、适用条件和验证状态。
保留帮助判断的经验，避免复制 Task 历史、测试计数或将某个样本参数变成所有项目的固定门槛。
