## 2026-10-11：文件夹整理范围收敛

MediaFlow Slice 44 的文件夹整理经历多轮修正。[完整旅程审查](../reviews/slice-44-folder-organize-audit.md)
发现了八组问题，既包含配置、文件名、部分失败、分页、附件和 Worker 状态等实际缺陷，
也暴露出原规划对复杂中断、配置切换及历史任务恢复的高要求。最初的架构调整仍保留了全部恢复承诺，
因此没有充分减少实现负担。用户进一步要求简化后，A 才明确收缩发现阶段的恢复范围。

本次合理范围以 Contract 提交 `7e96ebf314e4eab22a72d98028a775f248118138` 和规划提交
`7f9bec8896ce5a30ecba5ea9a55924b8f2df7af3` 的历史版本为准：保留正常文件夹整理与所有安全边界，
将无法证明安全续跑的未冻结发现，允许处理为保留记录、说明原因、明确停止后由用户重新发现。
这记录的是已经达成的范围与规划决策，不代表实现完成、审查 PASS、性能改善或开发成本已经下降。
后续状态应查 Git、当前 Slice/Task 和实际验证，不能从本文推断。

## 1. 先确定用户需要的完整能力，再选择保障它的机制

定义 Slice 时，先写清入口、状态、操作、成功、失败和恢复。文件夹整理的主旅程是：
选择目录或文件 → 有界后台发现 → 查看来源与排除原因 → 精确预览 → 独立确认执行 → 查看逐项结果。
后台队列、游标、观察记录、请求关联和锁，只在支撑这些承诺时才有必要。

“每页精确续跑”“任何并发都不丢未落盘工作”“所有历史异常自动修复”是更强的连续性能力，
不能仅因底层可以设计出这些机制，就将它们加入首批验收。也不能先承诺，再把实现困难交给 Developer
逐个打补丁。A 应在 Contract 中明确连续性需要达到什么程度，以及中断后可以接受什么用户结果。

## 2. 将普通正确性、安全约束和增强恢复分开判断

| 类别 | 本次例子 | A 的取舍 |
|---|---|---|
| 普通功能正确性 | 配置未生效、合法长名称使批次卡住、读取失败却显示完成、分页误计、Trailer 被当主片 | 保留为必修问题；发生频率低也不使已承诺行为失效变得合理 |
| 安全与数据完整性 | 来源越界、错误配置绑定、重复执行、静默覆盖或删除、旧 Worker 越权发布 | 始终保留；不能以简化或低概率为由取消 |
| 更强的自动恢复 | 响应丢失同时切换根目录仍自动找回、所有旧重复记录自动恢复、任意竞态精确续跑 | 评估价值与成本；本次经明确授权缩减，并保留可完成的安全替代路径 |

判断时同时看发生可能性、失败后果、替代路径和修正成本。本次没有生产频率统计，
“复合工况可能少见”只是取舍判断，不能写成已验证概率。简单计数错误即使出现在极端分页下，
通常也值得直接修正；不能因样本极端而要求重建调度或恢复框架。

## 3. 用明确的安全恢复降低连续性要求

只有确认发现阶段没有媒体变更、旧尝试可以被安全停止、记录与已落盘发现仍可查看时，
“明确停止后重新发现”才是可接受恢复。页面仍需说明失败阶段、保留了什么、是否发生媒体效果，
以及继续或新建发现的具体动作。一个泛化的“重试”按钮不满足这些条件。

零媒体变更不等于任意重提都安全：发现会创建持久任务记录。未知提交必须证明原申请，
否则保持未确认状态并提供原生查看与解决入口；不能猜另一个根目录或配置版本，也不能自动重复提交。
新发现应是可见的新尝试，不能重置旧任务预算、抹去拒绝原因或改写已经冻结的来源清单。

这项经验可用于其他可重新计算的只读分析阶段。已发生或可能发生真实写入的阶段，
仍需从持久状态和效果确定性恢复；成功项、不确定写入和历史授权不能套用“重新做一遍”。
本次也保留正常暂停、继续和取消，没有为了简化而移除普通控制能力。

## 4. 减少承诺属于实质 Contract 变更

如果修改改变 Required Outcome、Required Surface、Safety 或验收含义，就不能称为事实性澄清。
本次把必须无缝续跑改为允许安全停止后重新发现，确实减少了恢复义务，因此记录为
`PARTIAL / RESCOPE`，明确旧承诺作废部分、新承诺、仍有效的实现事实和 Deferred。

原 Base 仍代表同一能力的真实起点，所以本次保留 Slice ID 与 Base，修改后的 Contract 为 ACTIVE；
旧 FIX REQUIRED 审查和未完成事项保留，不伪造 PASS。Contract 先提交，再交给 B 重新判断当前 Task
是继续、合法调整还是重规划。若业务边界已经实质改变到原 Base 不再合适，应按现行工作流处理新 Slice，
不能为了缩小审查范围随意移动 Base。

本次用户明确授权 A 代替 B 规划，这是披露过的例外；B 的独立实现审查和 A 的全 Slice 最终审查仍分开。
这不是今后 A 自动接管 Task 规划、常规审查或实现的依据。

## 5. 复杂度需要分别评价

设计承诺、现有代码耦合、跨层实施和验证成本应分别判断。范围变小不会自动缩短已有实现，
也不保证更低测试等级。复用现有 Worker、Storage、过滤与附件规则、预览和 Executor，
比为发现增加通用框架更符合本次范围；仍须核实这些机制的语义和接口能否正确接通。

本次设计复杂度下降，但配置发布、并发入队、持久状态兼容和执行交接仍有较高风险，
因此 High / T4 保留合理。A 不应以文件行数、类数量或未经实施验证的百分比来宣称方案更简单。

## 6. 最终审查按当前 Contract 收敛

最终审查仍覆盖 Slice Base..Implementation Head 和完整用户旅程。配置需要验证实际发布与运行时消费；
Web 需要验证真实页面，而不是仅相信领域注入测试或后端成功。已有缺陷证据在缩减后仍有效的部分继续检查。

明确 Deferred 的更强恢复能力不能自行回流为 blocker；若其中暴露错误配置绑定、虚假完成或越权等
仍在范围内的缺陷，则依然是问题。P2/P3、wording、可选证明和未来功能不单独阻止 PASS。
满足当前 Contract 后按现行工作流一次性收尾，之后再另开一轮选择下一个大 Slice。
